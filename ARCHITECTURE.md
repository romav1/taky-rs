# taky-rs — architecture

- Status: **Proposed** (T-04, arch01, 2026-10-18; updated in T-05: D-8…D-21, limits, ADR-007). Becomes normative once ADR-001..007 are Accepted and Gate G-1 passes.
- Normative inputs: `shared/decisions/ADR-000-customer-requirements.md` (R1 full compatibility, R2 platforms,
  R3 `-rs` names, R4 MIT), ADR-001..007, behavioral spec `shared/spec/` (an01; if it diverges
  from this document on *behavior*, the spec wins; on *structure*, this document wins).
- Original: `taky/` v0.9 (Python, ~1.9k SLOC). References such as `cot/router.py:route` point to `taky/taky/...`.

---

## 0. Principles

1. **Drop-in replacement.** The same `taky.conf` (keys, defaults, search paths, relative paths), ports, CoT protocol,
   mgmt socket, Redis keys and value format, DPS directory (`upload_path`, `meta/*.json`, symlinks),
   `cert-db.txt`, certificates/p12, data package. The Python and Rust versions work on the same data (R1).
2. **Data compatibility is byte-exact where that is cheap** (CoT XML serialization, meta JSON, cert-db,
   ini on `takyctl setup`), otherwise semantic. The "byte-exact/semantic/may differ" matrix is T-05.
3. **Deliberate deviations** from the original are allowed only toward security/robustness
   (XXE, limits, memory leaks, slow clients) and are listed in §17; each is confirmed by pm01/the customer.
4. **Core without I/O (sans-IO).** Parsing, models, routing — synchronous/deterministic code, testable
   without a network (port of `taky/tests` 1:1). Network, TLS, processes — a thin shell.
5. No `unsafe` (except an agreed ADR), no `unwrap()` in network/parsing code, no C dependencies
   except `ring` (asm/C, cross-compiles). No OpenSSL.

### 2.1 CLI parity rules (clap 4)
- Names/short flags/positional arguments/defaults — as in argparse. `infer_long_args(true)` —
  argparse accepts prefixes of long options (`--p12` → `--p12_pw`, `--no-i` → `--no-install`).
- Exit codes: argument parse error — 2 (as in argparse and clap); `takyctl` without a subcommand — usage on **stdout**,
  code 1; an exception in a command — message `"<cmd> failed: <err>"` on stderr, code 1; `taky-rs` — 1 on
  a startup error/unhandled error, 0 on normal termination via SIGTERM/SIGINT.
- `--version` prints `"<prog> version <VERSION>"` (prog = basename of argv[0], i.e. `taky-rs version …`).
  The value of `VERSION` is a question for the customer (Q-4 in §19).
- `-d` (`taky-rs`) is accepted and ignored (PDB on SIGUSR1 makes no sense in Rust; we log at `debug`).
- `--help` texts need not match (T-05 matrix); CLI error messages that the operator sees
  (`ERROR: ...`) match textually.

## 4. Data flows

### 4.1 CoT server (`taky-rs`)

```
          TCP :8087 / TLS :8089                         monitor TCP (mon_ip:mon_port, only with SSL)
                  │                                                 │
          accept task ──(TLS handshake ≤10 s, tokio-rustls)         │
                  │  PeerIdentity (serial, CN) from client cert     │
                  ▼                                                 ▼
  ┌─────────── client conn task (1 per socket, dev02) ────────────────────────┐
  │ read half: bytes ─► CotDecoder (taky-cot) ─► Element ─► Event::from_element│
  │            stats.num_rx++/last_rx; CotLogger (log_cot)                     │
  │            UnmarshalError ⇒ log + log_cot(__taky_err), continue            │
  │            XmlError/limit ⇒ disconnect("XML Syntax Error")                 │
  │ write half: Outbox rx (bounded) ─► write_all(frame) ─► socket              │
  └───────────────┬────────────────────────────────▲──────────────────────────┘
                  │ HubCmd::{Connected, Event,     │ Frame = Arc<[u8]> (event
                  │   Disconnected} (mpsc, bounded)│   serialized ONCE)
                  ▼                                │
  ┌──────────── Hub actor (1 task, dev02) ─────────┴──────────────────────────┐
  │  CertDb (ban on connect/kickban)        mgmt requests (status/kickban/ping)│
  │  Router (dev01, sans-IO):                                                 │
  │    on_event: monitors ◄ packet_rx │ t-x-c-t ⇒ pong │ a-* ⇒ ident │       │
  │              max_ttl │ GeoChat/marti/broadcast │ persist.track()         │
  │    send_persist on connect; prune every 10 s                             │
  │  Persistence: Memory (in the actor) | Redis (ConnectionManager, timeouts)│
  └───────────────────────────────────────────────────────────────────────────┘
                  ▲
   unix socket {root_dir}/taky-mgmt.sock ─ mgmt task (NUL-JSON) ─ HubCmd::Mgmt(oneshot)
```

The order of handling an incoming event in `Router::on_event` repeats `TAKClient.feed` + `COTServer.mon_packet`
+ `COTRouter.route`: (1) a copy to all monitor clients (only if the source is not a monitor); (2) no `type` →
stop; (3) `t-x-c-t` → pong to the source, stop; (4) `a*` and detail=TAKUser and the source is not a monitor → update the
client's `user`; (5) `max_persist_ttl`; (6) GeoChat → broadcast/group/uid; marti → by callsign; otherwise
broadcast (+`persist.track` only in broadcast, as in the original). Details and edge cases — an01 spec.

### 4.2 DPS (`taky_dps-rs`)
`accept` (TCP :8080 or TLS :8443, client cert **optional**) → `PeerIdentity` → middleware removes
the `X-USER`, `X-SERIAL_NUMBER`, `X-ISSUER`, `X-REVOKED`, `X-NOT_BEFORE`, `X-NOT_AFTER` headers sent by the client
(only in TLS mode, like the gunicorn worker) and inserts the computed ones → axum handler → `RequireAuth`
(no `X-USER` → 401, `X-REVOKED` present → 403) → `MetaStore` (files in `upload_path`, `meta/{UID}.json`,
symlink `meta/{hash}.json → {UID}.json`) → response. Upload is streamed to disk (no buffering in RAM).
Access log to stdout in the gunicorn format `%(t)s "%(r)s" %(s)s %(b)s "%(a)s"`. Details — ADR-004.

### 4.3 takyctl-rs
- `status`/`kickban`: unix socket → `{"cmd": ...}\0` → response up to `\0`, overall timeout 5 s, recv timeout 1 s.
- `setup`: `Ini::write` → `taky.conf`; `certgen::make_ca` → `ca.crt/ca.key`; `make_cert(server)` →
  `server.crt/key/p12`; `CertDb::add`.
- `build_client`: copy of `server_p12` → `certs/server-<uuid4>.p12`; `make_cert(client)` → p12; `CertDb::add`;
  `preference.pref`, `MANIFEST/manifest.xml`; zip → `./<name>.zip`. As built (S-322, review-3E): the package is
  assembled **in memory** (no `taky-cert-*` temp dir), zip entry order = manifest, then the manifest `Contents` order
  (Python: `os.walk` order, FS-dependent, non-normative); a name containing `/` is refused up front (D-25).
- `systemd`: generation of `taky-rs*.service` units (§18), `systemctl daemon-reload/enable/start`.
- `kickban` only sends the mgmt request; the **server** revokes (D-11). Server down ⇒ `Is taky running?`, exit 1
  (parity; no offline cert-db fallback — review-3E, open for the customer at G-2).

## 5. Concurrency model (ADR-001)

- **tokio** multi-thread runtime (`worker_threads` defaults to the CPU count; on Pi Zero 2/3 — 4 cores).
- **Hub actor**: a single task owns `Router` + the client table + `CertDb` + `Persistence`.
  Everything that changes routing is `HubCmd` messages through a bounded `mpsc`. No `Mutex` on the hot path.
- **Task per connection**: reads and parses (the CPU work of XML is spread across cores), writes from its own
  `Outbox` queue. Event serialization is done once (`Arc<[u8]>`), fan-out is cloning the `Arc`.
- **Why an actor and not shared state** (`Arc<RwLock<Router>>`):
  1. The original is a single-threaded select loop: events are globally ordered, `track` runs before fan-out,
     `send_persist` is atomic with respect to fan-outs. The actor reproduces this without reasoning about locks;
     with an `RwLock` we would have to hold the write lock across a Redis `await` (forbidden) or lose ordering.
  2. `Router` stays simple `&mut self` code → a direct port of `tests/test_router.py`, determinism in tests.
  3. Load: target ~1000 events/s × 100 clients = 10⁵ `try_send`/s — a single thread copes with a margin
     (estimate ≤ 5% of a Pi 4 core; qa01 verifies in T-32). The bottleneck is parsing, and that is outside the actor.
  4. Downside: the actor is a serialization point; with slow Redis it blocks routing. Mitigation: Redis
     timeouts (§13). As implemented (S-309, ADR-001 errata 2026-10-25) `track`/`get_all` are awaited in the actor,
     bounded by 500 ms per command, 1 s connect, one reconnect attempt per 5 s while down. The fire-and-forget writer
     task (FIFO, so that reads in `send_persist` see earlier writes) is the fallback if T-32 (e) shows stalls.
- Blocking I/O (`log_cot` files, `cert-db.txt`, DPS) — `tokio::fs`/`spawn_blocking`; the actor has no
  file operations except `CertDb::revoke` (rare; via `spawn_blocking` with a wait).

## 6. Backpressure and slow clients

| Mechanism | Default value | Behavior | Original |
|---|---|---|---|
| Inbound `mpsc` conn→Hub | 1024 messages shared | `send().await` — the reader waits, the TCP window closes → natural backpressure for flooders | none (select loop) |
| Client `Outbox` | 8 MiB **or** 4096 frames | `try_send` from Hub; overflow ⇒ disconnect `"Slow client"` (warning), memory does not grow | `out_buff` without a limit — memory growth (D-3) |
| Shared frames | `Arc<[u8]>` | broadcast to N clients does not copy data | `tostring` per client |
| TLS handshake | 10 s | timeout ⇒ close, log `"SSL Handshake timeout"` | 10 s (as in the original) |
| Size of a single top-level element | 4 MiB | exceeded ⇒ disconnect `"XML Syntax Error"` | no limit (TODO in the original; libxml2 — ~10 MB per text node) (D-2) |
| Depth/attributes/names/nodes | 256 incl. the virtual `<root>` (as libxml2: 255 nested ok) / 256 / 1 KiB / 100 000 nodes per top-level element | same | depth 256 — libxml2 |
| Socket send | `write_all` with a 30 s timeout per frame | timeout ⇒ disconnect | non-blocking send |
| Number of connections | no limit (as the original), `ulimit` | — | — |
| mgmt request frame | 1 MiB without `\0` (`MGMT_MAX_FRAME`, S-313) | exceeded ⇒ the mgmt connection is closed | buffered without a limit (D-3 extension, review-3C) |

Slow-client policy (review-T-10 N-3, implemented in S-308, accepted in review-3B): the limit is enforced by the
`Outbox` implementation (taky-server; byte **and** frame accounting). On `try_send` → `Full` the Router drops that
frame, logs WARNING, calls `Outbox::close("Slow client")` and removes the client from its table immediately (no
further fan-out, also not to later recipients of the same fan-out); on `Closed` it drops and removes without `close`.
Counters `Router::dropped_frames()` / `slow_disconnects()` (debug only, not in mgmt). Consequences for the Hub:
`Disconnected{id}` for an id the Router already removed is a no-op; events still arriving from a removed id are dropped
(DEBUG); mgmt `status`/kickban (via `Router::clients()`) no longer list the client before its socket is closed.
`Outbox::close` must be idempotent and must not block.

The values are constants in `taky-cot::limits`/`taky-server::limits`; moving them to `taky.conf` (new optional
keys, Python ignores them) — only after the customer's answer (Q-3).
A client's pending frames are not accumulated before the handshake completes: the client is registered in `Router` after the
handshake (in the original, events before the handshake were silently dropped — equivalent).

## 7. Error handling

- Libraries: `thiserror` enums (`IniError`, `ConfigError`, `XmlError`, `UnmarshalError`,
  `CotStreamError`, `PersistError`, `PkiError`, `DpsError`). Binaries: `anyhow` only at the top level.
- An error of one client does not affect others: everything related to a connection ends only its task.
  Connection error classes → disconnect reason strings match the original (`"Client disconnected"`,
  `"XML Syntax Error"`, `"User banned"`, `"Banned"`, `"Server shutting down"`, `"SSL Handshake timeout"`,
  the text of the io/TLS error).
- `UnmarshalError` → `debug` log + a `log_cot` entry with `<__taky_err>` (as the original), the connection lives.
  Other event processing errors → `error` log "Unhandled exception parsing Event", the connection lives.
- Panics: `panic = "unwind"` in release; a panic in a conn task = client disconnect (`error` log).
  Termination of the Hub actor (panic/error) ⇒ `critical` "Unhandled exception", shutdown, exit 1.
- Redis: connection errors are not fatal — the `rds_ok` latch ("Lost connection to redis" / "Connection to redis
  restored"), as in the original; corrupted values are deleted (purge) as in the original.
- Config: parse errors → the same messages and exit codes as in `__main__.py` (an01 spec); errors on which
  Python prints a traceback (ValueError, Duplicate*) — a readable message with the same code 1 (D-13).
- Internal invariants whose violation crashed the server in Python (B2/B4, D-8/D-10) are, in Rust, an error of a single event/request.
- `unwrap()/expect()` are forbidden outside tests and outside provably-invariant places with a comment (clippy
  `unwrap_used`, `expect_used` = deny in network/parsing crates).

## 10. Signals and graceful shutdown

- `taky-rs`: SIGTERM and SIGINT → `Shutdown::trigger()` (CancellationToken). The sequence is like
  `COTServer.shutdown()`: log "Sending disconnect to clients" → all clients are closed with reason
  `"Server shutting down"` (without waiting for queues — like the original; a 2 s limit for TLS
  close_notify) → close listeners → close mgmt and delete `taky-mgmt.sock` → log "Stopped" → exit 0.
  SIGUSR1 — ignored (with `-d` — a debug log). A shutdown error → `critical`, exit 1.
- Startup: if `taky-mgmt.sock` exists — ping (`{"cmd": "ping"}\0`, 1 s); a reply ⇒ error
  "Taky already appears to be running", exit 1; none ⇒ delete it and take it over. A mgmt bind error is not fatal.
  A stale file that cannot be removed must fail startup like Python's `os.remove` exception (`Unable to start COTServer: …`,
  exit 1) — review-3C N-2; as of d0707b4 Rust logs DEBUG and continues without mgmt.
- As implemented (S-314): logs `Got SIGTERM` / `Got SIGINT` (Python is silent on SIGINT — non-normative, compat 1.4.17);
  banner `INFO:root:taky-rs v<ver>` (G-3); `Listening for <mode> on <ip>:<port>` is logged after the bind with the bound
  address (Python: before, with the config value; non-normative). Whole shutdown ≤ 10 s, else CRITICAL
  `Exception during shutdown`, exit 1. A Hub panic ⇒ CRITICAL `Unhandled exception: …`, shutdown, exit 1.
- `taky_dps-rs`: SIGTERM/SIGINT → stop accepting, wait for active requests up to 30 s (like gunicorn's
  `graceful_timeout`), exit 0.
- The Hub does **not** drain its queue after cancellation (as implemented, S-312: `biased` shutdown branch, then all clients
  are closed with `"Server shutting down"`); Redis writes are awaited in the actor, so there is no writer buffer to flush
  (ADR-001 errata 2026-10-25). Connection tasks get ≤ 2 × `CLOSE_TIMEOUT` to finish.

## 15. Extension points (not implemented now, but not closed off)

- `Persistence` — an enum; a new backend = a new variant (no `dyn async`).
- Routing filters/policies — a `Router::policy` hook (by default "as the original"), e.g. enforcing
  callsign = certificate CN (mentioned in `README_SECURITY.md` as unimplemented).
- Additional DPS endpoints — a separate `axum::Router` merge.
- Metrics (Prometheus) — via `tracing`/a separate port, off by default.
- Transports (UDP/multicast CoT, protobuf TAK v1) — new conn tasks, the same `HubCmd`.
- Metrics for Hub command processing time (for risk R8).

## 18. Paths, parallel installation with the Python version

- Default paths are **the same**: `/etc/taky/taky.conf`, `/etc/taky/ssl/*`, `/var/taky`, `/var/taky/dp-user`,
  `{root_dir}/taky-mgmt.sock` (R1). This is the "work on the same data" requirement.
- Binaries and units do not conflict: `taky-rs.service`, `taky-rs-cot.service`, `taky-rs-dps.service`
  (site: `taky-rs-{hostname}[-cot|-dps].service`).
- **Conflict (escalated by pm01, Q-1):** the Python and Rust servers **cannot run simultaneously** on the same
  host with the same config — identical ports (8087/8089/8443/8080) and one mgmt socket (the second one to start
  exits with "Taky already appears to be running" or a bind error). Installing side by side — yes, running simultaneously — no.
  Proposal: the `taky-rs*.service` units get `Conflicts=taky.service taky-cot.service
  taky-dps.service` (and we do not touch the reverse). Also `EnvironmentFile`: we propose `/etc/default/taky-rs`
  (`-/etc/default/taky-rs-{host}`) — a deviation from the unit's byte parity (Q-2). Decision — `shared/spec/gate1-questions.md` G-1, G-2.
  **As built (S-323, review-3E; G-1/G-2 accepted in ADR-008):** every `taky-rs*` unit has `Conflicts=` **and**
  `After=` on all three Python units of the same mode (`After=` makes systemd stop the Python unit before starting the
  Rust one, so the ports are free); `EnvironmentFile=-/etc/default/taky-rs[-<host>]` in the CoT **and** DPS units;
  `Description=taky-rs …`; ExecStart = absolute path when `taky-rs`/`taky_dps-rs` sit next to `takyctl-rs`, else the
  bare name. Neither `setup` nor `systemd` writes the environment file (Python writes none either).
- `takyctl-rs` and `takyctl` write the same `cert-db.txt`; Rust — under `flock` with a re-read (D-11), Python — without locks; running
  two CLIs at once is the same race as in the original. We add writing via tmp+rename (atomic).
- Redis: identical keys — Rust and Python on different hosts with a shared Redis and the same `hostname` see the same
  events (as intended by R1).

## 19. Risks and questions

Main risks (the full top-10 is in T-05):
1. **XML parser strictness ≠ libxml2** (what counts as an error ⇒ disconnect). Mitigation: differential fuzzing
   of the decoder against lxml (qa01, an01 vectors), explicit checks (duplicate attributes, end names, entities, UTF-8).
2. **Byte-exact serialization like lxml** (ASCII + `&#NNN;`, `<x/>`, normalization of `\t`/`\r` in attributes, tail
   of `detail`). Mitigation: golden vectors from Python (`etree.tostring`) in `shared/spec/vectors`.
3. **TLS compatibility with old clients**: rustls does not support RSA key exchange, TLS ≤1.1, SHA-1
   certificate signatures. Modern ATAK/WinTAK/iTAK — ECDHE + TLS1.2/1.3. Verification on the customer's device.
4. **p12 for Android**: own encoder (3DES/SHA-1, iter 1/2048) — verified with openssl, python
   `cryptography`, p12-keystore and a real ATAK (customer).
5. **Cross-build in the container is impossible**: static.rust-lang.org is closed by proxy policy (403, confirmed by pm01,
   bypass forbidden), no Docker daemon ⇒ ARM/musl/Docker are built in GitHub Actions or on the customer's machine
   (ADR-007); in the container — only x86_64-gnu.
6. Redis latencies block the actor — timeouts and a separate writer (§5, §13).
